<WhyItMatters>
A swerve drivetrain has 12 devices (four modules, each with a drive motor, a steer motor and an encoder) plus a gyro.
Each needs a CAN ID, a gear ratio, a mounting position and a calibrated encoder offset, and one wrong number makes the robot crawl sideways.
CTRE's Tuner X **swerve project generator** (SwerveGen) measures that hard part with you and writes the code, so you can spend your time on driving.
</WhyItMatters>

## Generated for you, written by you

You answer a few questions in Tuner X: motor types, CAN IDs, gear ratios, wheel size, module positions. It also reads each encoder to find its offset.
It then writes a project. You read the generated files, but you do not edit them.

| Generated for you (do not hand-edit) | Written by you |
| --- | --- |
| `TunerConstants`: CAN IDs, gear ratios, wheel radius, module positions, encoder offsets, drive and steer gains | Drive commands (`DriveCommands`): joystick curve, deadband, which request to apply |
| The base drivetrain class `TunerSwerveDrivetrain` (inside `TunerConstants`) that builds the motors, encoders and gyro | Additions in `CommandSwerveDrivetrain`: vision, PathPlanner setup, special requests |
| `CommandSwerveDrivetrain` skeleton: `applyRequest`, SysId routines, simulation thread | Button bindings and the default command in `RobotContainer` |
| A telemetry class that publishes the drive state | Anything the robot does with the pose |

## How the drivetrain is created

`TunerConstants` also holds a factory that passes all constants into your drivetrain class.

<AnnotatedCode
  file="rebuilt2026-6.4/create-drivetrain"
  title="TunerConstants.java"
  notes={[
    { lines: '1', text: 'Call this <strong>once</strong>. It builds all the hardware, so a second call would try to claim the same CAN devices again.' },
    { lines: '3', text: 'Drivetrain-wide constants (CAN bus name, gyro ID) plus one block per module.' },
  ]}
/>

`RobotContainer` calls it in one line, and that is the only place the drivetrain is made:

```java
public final CommandSwerveDrivetrain drivetrain = TunerConstants.createDrivetrain();
```

## When to regenerate

Regenerate in Tuner X whenever the **hardware** changes: a motor or encoder with a new CAN ID, a swapped module, a different gear ratio or wheel, or modules re-aligned after a repair. Re-measure the encoder offsets after any re-assembly.

If you edit a generated file by hand, the next regeneration overwrites your edit silently, and the robot suddenly behaves differently. Put your own logic in `CommandSwerveDrivetrain` additions and in commands instead. The team's file marks what it added, such as the vision code and PathPlanner setup.

<GoDeeper title="what the generated gains are not">
The generated drive and steer gains are a starting point. Each team characterizes its own robot with SysId and tunes the values in `TunerConstants`.
That edit is an exception: it changes a number, not the structure. Note it, and re-apply it if you ever regenerate.
</GoDeeper>

## Checkpoint

<Checkpoint lesson="6.4">

<details>
<summary>The robot is rebuilt with a module swapped for a spare. What do you do in the code?</summary>
Regenerate (or at least re-measure) in Tuner X, because the spare's encoder has a different offset. Do not fix it by nudging a number in a driving command.
</details>

<details>
<summary>A teammate wants to add a deadband by editing TunerConstants. What do you tell them?</summary>
The deadband belongs in the drive command, which you wrote. TunerConstants describes hardware, and a regeneration would erase the edit.
</details>

</Checkpoint>

## Recap

<RecapCard>
- SwerveGen writes the hard, hardware-specific part: constants, the base drivetrain, a command wrapper.
- You write the driving: commands, bindings, extra drivetrain features.
- `TunerConstants.createDrivetrain()` is called once, in `RobotContainer`.
- Hardware changed means regenerate. Hand edits in generated code get lost.
</RecapCard>
