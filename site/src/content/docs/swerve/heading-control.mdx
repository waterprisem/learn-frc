## Resetting the pose or the heading

Odometry needs a starting point, and sometimes you must give it a new one.

| When | What you reset | Why |
| --- | --- | --- |
| Start of autonomous | The pose, to the path's start pose | The path assumes the robot starts exactly there |
| Driver says "forward is wrong" | The heading only | Field-centric forward drifted from the real field direction |

In the team's 2026 code, PathPlanner's `AutoBuilder` is given `this::resetPose` so it seeds the pose at the start of an auto.
This code has no driver "zero heading" button. In CTRE's example project that button calls `seedFieldCentric()`, which makes the robot's current facing the new field-centric forward without moving the position. (2026)

## Turning to face a target

Say the robot is at (2, 3) and the target is at (6, 6) meters, both in the field frame.

1. Subtract: the difference is 4 m in x and 3 m in y.
2. The angle to the target is `atan2(dy, dx)` = `atan2(3, 4)`, about 37 degrees.
3. Hand that angle to a controller as the **target heading**.

<AngleToTarget />

Use `atan2`, not `atan`: it takes the two differences separately, so it gets the correct quadrant. The team computes this with `PhotonUtils.getYawToPose`, passing poses with zero rotation so the result is the field-frame angle.

## Driver translates, a PID turns

CTRE's `FieldCentricFacingAngle` request takes the driver's x and y speeds like normal field-centric driving, plus a target direction. A built-in **heading PID** turns the angle error into the rotation rate. The right stick is not used.

## Wrap-around

Angles repeat every 360 degrees. If the robot faces 179 degrees and the target is -179 degrees, the plain error is -179 - 179 = -358 degrees, and the PID would spin almost a full turn.
The real error is 2 degrees. **Continuous input** tells the controller the range wraps (here -180 to 180 degrees), so it always takes the shortest way round.

CTRE's `FieldCentricFacingAngle` sets this up in its heading controller, so you get it for free. With a plain WPILib `PIDController` you would call `enableContinuousInput(-Math.PI, Math.PI)` yourself.

<GoDeeper title="why kP 7 can still oscillate">
kP is radians per second per radian of error. With kP 7, a 1 radian (57 degree) error asks for 7 rad/s, which is more than a robot can turn, so the output saturates.
Too much kP overshoots the target and swings back and forth. Lower it until the robot settles, as in lesson 3.5.
</GoDeeper>

## Checkpoint

<Checkpoint lesson="6.6">

<details>
<summary>Why reset the pose at the start of autonomous?</summary>
The path is drawn from a specific starting pose. If odometry thinks the robot starts somewhere else, every path point is offset by the same amount.
</details>

<details>
<summary>Why does a facing-angle controller need continuous input?</summary>
Angles wrap, so 179 and -179 degrees are 2 degrees apart. Without it the error looks like 358 degrees and the robot turns the long way.
</details>

</Checkpoint>

## Recap

<RecapCard>
- Reset the pose at the start of autonomous; reset only the heading when the driver's forward is off.
- Angle to a target is `atan2(dy, dx)` of the pose difference, in the field frame.
- `FieldCentricFacingAngle` lets the driver translate while a heading PID turns the robot.
- Continuous input makes the error wrap to the shortest way round.
</RecapCard>
