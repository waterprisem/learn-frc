<WhyItMatters>
Imagine two pieces of code both telling the same shooter motor what to do: one says 6 V, the other says 0 V. The wheel stutters and nobody knows why.
The fix is a rule: every mechanism has exactly one owner, and everything else asks that owner.
</WhyItMatters>

## One mechanism, one owner

A **subsystem** is a class that owns one mechanism: its motors, its sensors, and its configuration. No other class creates or touches that hardware.

Everything else goes through the subsystem's small public methods:

- **Commands** call methods such as `setFlywheelVoltage(6.0)`. They never hold a motor.
- **Methods are named for what they do, with units in the name**, like `getFlywheelVelocityRPS()`. The name says the unit, so nobody guesses.
- **`periodic()`** reports what the mechanism is doing. It observes; it does not decide.

## Why a single owner

When every output to a motor goes through one subsystem, the scheduler knows exactly who is using it. It can then guarantee that two commands never run on the same subsystem at the same time. Lesson 2.4 shows how a command claims a subsystem.

If a command built its own `TalonFX` instead, the scheduler would not know that command was driving the same wheel, and it could not stop the fight.

## The subsystem's methods

The subsystem is the mechanism's interface. Commands send it requests, and `periodic()` publishes the state about every 20 ms as **telemetry**: the live numbers you graph in AdvantageScope.

## Checkpoint

<Checkpoint lesson="2.2">

<details>
<summary>What state belongs to a subsystem, and what behavior belongs to a command?</summary>
The subsystem owns the hardware, its configuration and its telemetry. A command owns one behavior, such as holding a voltage while a button is pressed.
</details>

<details>
<summary>Why should a command not construct its own TalonFX?</summary>
It would bypass the mechanism's single owner. The scheduler could no longer tell which commands are using the motor, so it could not prevent two of them from fighting over it.
</details>

</Checkpoint>

## Recap

<RecapCard>
- One subsystem per mechanism owns its motors and sensors; nothing else touches them.
- Public methods are the interface, named with units, such as `getFlywheelVelocityRPS()`.
- `periodic()` reports state and never drives the motor.
- One owner lets the scheduler prevent two commands from fighting over a motor.
</RecapCard>
