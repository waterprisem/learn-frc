## What "open loop" means

The code sends a fixed voltage, 6 V, and never checks how fast the wheel actually turns. That is **open loop**.

The speed you get depends on things the code cannot see: battery charge, friction, a ball touching the wheel. The same 6 V can give different speeds on different days.

Lesson 3.1 closes the loop by measuring the speed and correcting it. First you need the open-loop version working, because the closed-loop one reuses its structure.

## The path from button to motor

```text
Xbox A or B  ->  binding  ->  SetFlywheelVoltageCommand  ->  FlywheelSubsystem  ->  TalonFX
```

The lab manual builds it from the motor outward: subsystem, command, bindings. The subsystem code was covered in lesson 2.7, so this lesson covers the two parts it did not.

## The command

The command carries a voltage and applies it for as long as it runs.

Bindings (lesson 2.5) use `whileTrue()` for A at `FORWARD_VOLTAGE` (6 V) and B at `REVERSE_VOLTAGE` (-4 V). A default command holds 0 V when no button is pressed.

Every 20 ms the subsystem publishes what the encoder says, so you can graph the wheel instead of trusting the animation.

<GoDeeper title="why the lab keeps the physics out of the subsystem">
The simulation helper is desktop-only code. If it lived inside the subsystem, deployable robot code would carry laptop physics.
Two contact points, one construction line and one update call, keep the boundary small enough to check at a glance.
</GoDeeper>

## Do it for real

<DoItForReal tools="WPILib simulator + AdvantageScope">
This is **Lab 3** in the team curriculum repository. Open the project folder `labs/Session 3 - Open-Loop Flywheel with TalonFX/assignment` as its own WPILib project. Do not edit `FlywheelSimulation.java`.

**See the goal first.** Open `solution/` in WPILib VS Code, run **WPILib: Simulate Robot Code**, choose **Teleoperated**, enable, and hold A. Then stop the simulation.

**Then build it, in the manual's order.** Search the assignment for `TODO Step` (Steps 1 to 7) and run **WPILib: Build Robot Code** before changing anything.

1. **Step 1, constants** in `Constants.java`: CAN ID 1, `FLYWHEEL_MOTOR_INVERTED` false, stator limit 80 A, supply limit 40 A, `FORWARD_VOLTAGE` 6.0, `REVERSE_VOLTAGE` -4.0.
2. **Step 2, configure the TalonFX** in `FlywheelSubsystem.java`: output config (inversion, coast) and both current limits with their enable flags.
3. **Step 3, public methods:** `setFlywheelVoltage`, `getFlywheelVelocityRPS`, `getFlywheelPositionRotations`.
4. **Step 4, telemetry:** publish both values in `periodic()`.
5. **Step 5, simulation:** construct the helper only when `RobotBase.isSimulation()`, and call `update()` in `simulationPeriodic()`.
6. **Step 6, command** in `SetFlywheelVoltageCommand.java`: requirement, `execute()`, `end()`, `isFinished()`.
7. **Step 7, bindings** in `RobotContainer.java`: A, B, and the 0 V default command.

Build after each step. Fix the first compiler error, not the last.

**Check it in AdvantageScope.** Connect to the simulator and graph these two topics:

- `/Subsystems/FlywheelSubsystem/Velocity RPS`
- `/Subsystems/FlywheelSubsystem/Position Rotations`

Do this sequence: idle 1 s, hold A for 2 s, release and wait, hold B for 2 s, release and wait.

**The lab's four tests**

- [ ] Test 1, idle: the wheel stays stopped and velocity is at or very near 0.
- [ ] Test 2, forward: hold A for about 2 s. Velocity is positive, position rises, and the wheel coasts to a stop on release.
- [ ] Test 3, reverse: hold B for about 2 s. Velocity is negative, position falls, and the wheel coasts to a stop on release.
- [ ] Test 4, scheduler handoff: hold A, then also hold B. The two commands never run together. Release both and confirm 0 V.

**You know it worked when** the graph shows a positive velocity plateau during A, a coast-down curve after release, a negative plateau during B, and another coast-down. Position rises going forward and falls going backward. The `Flywheel/Mechanism` widget animates both ways.

**On a real robot, also check**

- The CAN ID on the motor is 1, or the constant matches whatever it really is.
- Positive voltage spins the way the mechanism expects. If not, flip `FLYWHEEL_MOTOR_INVERTED`.
- The same 6 V gives a different speed than in simulation. That is the open-loop limit, and it is why lesson 3.1 exists.
</DoItForReal>

## Checkpoint

<Checkpoint lesson="2.8">

<details>
<summary>Why does <code>end()</code> set the voltage to zero?</summary>
The command ends whenever the button is released or another command takes over. Without a 0 V in `end()`, the last voltage request would keep driving the wheel.
</details>

<details>
<summary>Why might the same 6 V give a different speed on a real robot?</summary>
Open loop never measures speed. Battery voltage, friction, and load all change what 6 V produces.
</details>

<details>
<summary>In Test 4, why do A and B not fight over the flywheel?</summary>
Both commands require the flywheel subsystem, so the scheduler interrupts the older one when the newer one starts.
</details>

</Checkpoint>

## Recap

<RecapCard>
- Open loop sends a fixed voltage and never checks the speed.
- The path is button, binding, command, subsystem, TalonFX.
- The command requires the subsystem, applies voltage in `execute()`, and sets 0 V in `end()`.
- `periodic()` publishes `Velocity RPS` and `Position Rotations`; the simulation helper stays out of the subsystem logic.
- Verify with encoder graphs, not the animation alone.
</RecapCard>
