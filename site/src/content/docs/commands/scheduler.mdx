<WhyItMatters>
Imagine a driver holds the forward button and the reverse button at once. If both commands wrote to the motor, it would flip between two voltages, and the wheel would shake.
The scheduler prevents this by allowing only one command per subsystem at a time.
</WhyItMatters>

## One call runs everything

`Robot.robotPeriodic()` calls `CommandScheduler.getInstance().run()` every 20 ms. That one call is the **scheduler**, the part of WPILib that decides which commands run. Each loop it does this:

1. Runs every subsystem's `periodic()`.
2. Polls the **triggers** (button conditions, lesson 2.5) and schedules any commands they start.
3. Runs `execute()` on each scheduled command, checks `isFinished()`, and calls `end()` on the ones that stopped.

Your own code does not loop over commands. It only declares them, and the scheduler does the timing.

## Requirements: one owner per subsystem

A **requirement** is a subsystem a command promises to control. You declare it in the constructor.

    { lines: '4', text: '<code>addRequirements(flywheelSubsystem)</code> tells the scheduler this command controls the flywheel. Without it, the scheduler cannot protect the flywheel from other commands.' },

The rule: two commands that require the same subsystem cannot run together. When a second one is scheduled, the scheduler **interrupts** the first. Its `end(true)` runs, then the new command's `initialize()` runs.

| Command A requires | Command B requires | Result |
|---|---|---|
| Flywheel | Flywheel | B interrupts A. A's `end(true)` runs. |
| Flywheel | Elevator | Both run together. |

<GoDeeper title="when is the new command rejected instead?">
By default the new command wins. A command can opt out by overriding `getInterruptionBehavior()` to return `kCancelIncoming`. Then the new command is dropped and the old one keeps running. Most commands never need this.
</GoDeeper>

## Worked example: the scheduler handoff

In Lab 3, A runs the flywheel forward, B runs it in reverse, and a default command holds 0 V. All three require the flywheel. Test 4 asks you to hold A, then press B without releasing A.

| What you do | Who owns the flywheel |
|---|---|
| Nothing | Default command (0 V) |
| Hold A | Forward command. The default is interrupted. |
| Also press B | Reverse command. Forward gets `end(true)`. |
| Release both | The default resumes (0 V) |

Releasing A while B is still held does nothing to B, because A's command is already gone. Use the encoder telemetry, not only the animation, to confirm which command is driving.

<summary>What conflict does addRequirements prevent?</summary>
Two commands controlling the same subsystem at the same time. The incoming command interrupts the existing one instead.
</details>

<summary>The driver holds A, then also holds B. What does the flywheel do, and what runs on the A command?</summary>
The flywheel switches to the reverse voltage. The A command gets `end(true)`, which sets 0 V, and then the B command starts.

## Recap

<RecapCard>
- `robotPeriodic()` calls `CommandScheduler.getInstance().run()` every 20 ms, and that call drives everything.
- Each loop: subsystem `periodic()`, trigger polling, then `execute()`, `isFinished()`, and `end()`.
- `addRequirements(subsystem)` lets the scheduler enforce one command per subsystem.
- A new command that shares a requirement interrupts the old one, and the old one's `end(true)` runs.
</RecapCard>
