<WhyItMatters>
A raw `Commands.parallel` sends the elevator and the arm to their goals with no thought for each other. On a real robot that is how an arm ends up bent against the frame.
Lab 10 fixes it with one rule: look at where the arm is now and where it is going, then pick the order.
</WhyItMatters>

## Two categories of arm angle

The code sorts every arm angle into one of two categories.

| Arm angle | Meaning | Elevator may move? |
|---|---|---|
| -25 to 50 deg | **Travel envelope** (folded) | Yes |
| Outside that range | Extended or pointing down | Only after the right order is chosen |

`HOME` is 45 deg, inside the envelope. The downward intake pose is -90 deg, outside it. The limits are `SAFE_ARM_MOVEMENT_MIN_ANGLE_DEGREES` and `SAFE_ARM_MOVEMENT_MAX_ANGLE_DEGREES`.

## Which mover goes first

`safeGoToLevel` looks at two things: the **current** arm angle and the **target** arm angle.

| Current arm | Target arm | What moves first | Why |
|---|---|---|---|
| Outside the envelope | Any | **Arm** to `HOME` angle, then elevator, then arm to target | The arm must fold before the carriage moves |
| Inside | Outside | **Elevator**, then arm | The arm leaves the envelope only after the carriage is in place |
| Inside | Inside | **Both together** | Neither move creates a collision |

Check it against the constants. The faux intake leaves the arm at -90 deg, so the next move is arm-first. The named poses (`INTAKE`, `HOME`, `L1` to `L4`) have arm angles from -22 to 48 deg, all inside the envelope.

<GoDeeper title="what the shipped numbers do">
Every arm angle in the lab's pose table falls inside -25 to 50 deg, so a move such as `L4` to `HOME` is classified as parallel-safe, even though the lab text calls it arm-first.
The code is the ground truth. Watch the `Current Transition` topic to see which branch actually ran, and tighten the envelope in `Constants.java` if you want those moves sequenced.
</GoDeeper>

## Faux intake and the clearance line

The right trigger runs a pretend pickup that points the arm straight down. That is only safe if the pivot is high enough, so the command checks the **measured** elevator height against `SAFE_ARM_MOVEMENT_HEIGHT_METERS` (0.64 m) before moving anything.

1. Below 0.64 m: publish `BLOCKED` and move nothing.
2. At or above 0.64 m: remember the starting height, arm down, elevator dips to 0.64 m, elevator returns to the remembered height, then hold.

A blocked request deliberately schedules no motor command. The driver sees the rejection, and the robot does not quietly choose a different position.

## Checkpoint

<Checkpoint lesson="5.6">

<details>
<summary>Why can the faux intake run at L4 but not at L2?</summary>
L4 is above the 0.64 m clearance line, so the arm can point straight down without hitting the drivebase. L2 (0.42 m) is below it.
</details>

<details>
<summary>Why does the faux intake return to its starting height instead of always going to L4?</summary>
It captures the measured height when the command starts, so it works from any level above the line and returns to exactly where it began.
</details>

<details>
<summary>Why should the arm and elevator subsystems not reference each other?</summary>
Each subsystem should only control its own motors. The ordering rule involves both, so it belongs in the one place that already sees both: the command layer.
</details>

</Checkpoint>

## Recap

<RecapCard>
- Sort the arm angle into travel envelope or outside it, using measured angles.
- Current arm outside: arm first. Target arm outside: elevator first. Both inside: parallel.
- Clearance uses the pivot height above the carpet, and a blocked request moves nothing.
- The safety rules live in `RobotContainer`, with named constants and telemetry under `Superstructure/Safety`.
</RecapCard>
