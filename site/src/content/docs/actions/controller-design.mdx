<WhyItMatters>
In a match the driver has seconds to react and one pair of hands. If three similar buttons do three subtly different things, the wrong one gets pressed under pressure.
Team 1360 runs a robot from one Xbox controller, so every button has to earn its place.
</WhyItMatters>

## Start from the driver's flow

Do not start from the list of commands you wrote. Picture a cycle: drive to the game piece, pick it up, move to score, score, return. Each step the driver takes becomes **one intention**, and each intention becomes one named action from lesson 5.1.

Lab 9 shows the smallest version. `Home` is not a button at all, because it is what the robot does when the driver is not asking for anything (lesson 5.4). Three held buttons cover the rest: A for Intake, X for Score Speaker, Y for Score Amp.

## The control map

This is the Lab 11 solution map. Compare how each binding type matches how the driver uses it.

| Button | Action | Binding |
|---|---|---|
| A | Intake on the active side | `whileTrue` |
| Y | Switch active side, then intake on it | `whileTrue` |
| X | Score on the active side | `whileTrue` |
| B | Safe stow | `onTrue` |
| Right bumper | Score burst | `whileTrue` |
| Left bumper | Home on the active side | `whileTrue` |

Use `whileTrue` for something the driver holds and wants to stop by letting go. Use `onTrue` for a one-shot sequence that finishes on its own, like the stow.

## One button, one intention

Each button above answers a single question the driver asks: "intake", "score", "stow". The side is not a separate button. It is **state** that every action reads, so the same A button works on both sides of the robot.

The Y button comes closest to doing two things: it flips the side and intakes. The lab keeps it as one intention, "intake from the other side". If you added a separate side-toggle button, the driver would have to remember to press it first, and forgetting it would send the robot to the wrong side.

## Checkpoint

<Checkpoint lesson="5.3">

<details>
<summary>Why is the stow bound with `onTrue` and intake with `whileTrue`?</summary>
Intake should only run while the driver holds the button, so releasing cancels it. Stow is a sequence that finishes on its own, so one tap is enough.
</details>

<details>
<summary>How does `Commands.defer` let Y toggle the side each time?</summary>
It runs the lambda every time the command is scheduled, so each press flips the field and builds the command for the new side. A normal command would be built once and could not change.
</details>

<details>
<summary>Why not give the active side its own button?</summary>
A separate button adds a step the driver has to remember. Keeping side selection inside the intake intention means one fewer thing to get wrong.
</details>

</Checkpoint>

## Recap

<RecapCard>

- Design bindings from the driver's flow, one intention per button.
- `whileTrue` for held actions, `onTrue` for one-shots that finish themselves.
- Keep mode in a field that every action reads, so the same button works in either mode.
- `Commands.defer` builds a command at press time when it depends on state.

</RecapCard>
