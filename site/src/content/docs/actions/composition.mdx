<WhyItMatters>
Your robot now has an elevator, an arm, and a flywheel, each with a command that moves it to a setpoint. A driver does not think "elevator, then arm, then flywheel". They think "score".
**Command composition** snaps small commands into one **named action** that a single button can start.
</WhyItMatters>

## Four ways to combine commands

Each way answers one question: when is the group finished?

| Composition | Runs | Ends when |
|---|---|---|
| `Commands.sequence(a, b)` or `a.andThen(b)` | `a`, then `b` | `b` ends |
| `Commands.parallel(a, b)` or `a.alongWith(b)` | `a` and `b` together | **all** have ended |
| `Commands.race(a, b)` or `a.raceWith(b)` | `a` and `b` together | the **first** one ends; the others are cancelled |
| `Commands.deadline(main, a, b)` | `main`, `a`, `b` together | `main` ends; the others are cancelled |

Pick **parallel** when the parts cannot get in each other's way. Pick **sequence** when order matters. Use **deadline** when one command is the clock and the others only need to keep running while it counts down.

## The rule that makes it safe

A composed command **requires every subsystem its parts require**. Put the elevator, arm, and flywheel commands in one group and the group owns all three. While it runs, no other command can take them, and the scheduler hands them back only when the whole group ends.

A group also cannot contain two parts that need the same subsystem at the same time. That is why Score Speaker below uses a fresh elevator command in each stage instead of running one for the whole action.

## Decorators on one command

Decorators are methods you chain onto a command to change when it ends.

| Decorator | Effect |
|---|---|
| `.until(condition)` | Ends the command when the condition becomes true |
| `.withTimeout(seconds)` | Cancels the command after that many seconds |
| `Commands.either(a, b, condition)` | Chooses `a` or `b` when it starts |
| `.withName("Score Speaker")` | Labels the command for logs and the scheduler view |

Lesson 5.2 uses `until` and `withTimeout` in the lab code. Lesson 5.3 uses `either`.

## Worked example: Score Speaker

Lab 9 builds Score Speaker as a strict sequence, so you can see each stage. A mechanism command like `SetElevatorHeightCommand` never finishes on its own. A `deadline` ends it by pairing it with a command that does finish.

Which command is running when:

| Stage | Running | Stage ends when |
|---|---|---|
| 1 | elevator to Speaker height, `waitUntil(elevatorAtScoreSpeaker)` | the elevator is ready |
| 2 | elevator hold, arm to Speaker angle, `waitUntil(armAtScoreSpeaker)` | the arm is ready |
| 3 | elevator hold, arm hold, flywheel at Speaker velocity | never; button release cancels it |

The group stays scheduled between stages, so a default command never sneaks in and moves a mechanism.

## Checkpoint

<Checkpoint lesson="5.1">

<details>
<summary>Why is Score Speaker a sequence while Intake is a parallel?</summary>
Intake moves the elevator, arm, and flywheel to positions that are safe to reach in any order, so they can run together. Speaker is deliberately serial in the lab: elevator first, then arm, then flywheel, so you can see each stage and so the flywheel only spins once the others are ready.
</details>

<details>
<summary>What does `Commands.deadline(Commands.waitUntil(t), moveCommand)` do?</summary>
The move command runs while the wait command decides when the stage ends. When the trigger becomes true, the wait ends, so the deadline ends and cancels the move command.
</details>

<details>
<summary>The group contains elevator, arm, and flywheel commands. Which subsystems does it require?</summary>
All three. A composition requires the union of its parts' requirements, so no other command can use any of them until the group ends.
</details>

</Checkpoint>

## Recap

<RecapCard>

- Sequence runs in order, parallel ends when all end, race ends when the first ends, deadline ends when its main command ends.
- A composition requires every subsystem its parts require.
- `until`, `withTimeout`, and `either` change when or what a command runs.
- Name every action with `withName` so you can read it in logs.

</RecapCard>

<GoDeeper title="decorators and the factory methods are the same thing">

`a.andThen(b)` and `Commands.sequence(a, b)` build the same kind of group, and so do `alongWith` and `Commands.parallel`, and `raceWith` and `Commands.race`. The Lab 9 solution uses the `Commands` factory form for the groups and `andThen` once, inside Score Amp. Choose the form that reads best. The factory form is easier to read when there are three or more parts.

</GoDeeper>
