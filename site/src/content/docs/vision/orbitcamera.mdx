<WhyItMatters>
On a real team you spend more time reading code you did not write than writing new code. `OrbitCamera` is a class the team wrote once and reuses for every camera on the robot. You will use it, not rewrite it, so the skill here is reading it fast.
</WhyItMatters>

## How to read an unfamiliar class

Go in this order, and ask one question at each stop:

1. **Fields:** what does this class own?
2. **Constructor:** what must the caller provide, and what is set up?
3. **Public methods:** what can other classes ask it to do?
4. **Callers:** who actually uses it, and when?

## 1. Fields: what it owns

`OrbitCamera` wraps one physical camera. It owns the field layout, the `PhotonCamera`, a `PhotonPoseEstimator`, the robot-to-camera transform, and the latest results.

## 3. Public methods: what it offers

Notice what the class does **not** do. It never calls `addVisionMeasurement` itself. It hands out its estimator and results, and the caller decides what to do with them.

`updateEstimationStdDevs` (lesson 7.2) is the other public method: it filters results by ambiguity and distance and sets the standard deviations.

## 4. Callers: who uses it

Search for where `OrbitCamera` appears. The drivetrain creates three of them, one per camera, and calls `updatePose()` from its `periodic()`, so it runs every 20 ms loop.

<GoDeeper title="why the class has no periodic method">
`OrbitCamera` is not a subsystem. It has no `periodic()` of its own and is never registered with the scheduler. The drivetrain, which owns the pose, drives it from its own `periodic()`. That keeps one place responsible for pose.
</GoDeeper>

## Checkpoint

<Checkpoint lesson="7.3">

<details>
<summary>You mount a new camera on a different robot. What do you pass to the constructor?</summary>
The new robot-to-camera transform and the camera's name exactly as shown in PhotonVision.
</details>

<details>
<summary>Why does the drivetrain, not OrbitCamera, call addVisionMeasurement?</summary>
The drivetrain owns the pose. OrbitCamera only produces estimates and trust values, which keeps it reusable for any number of cameras.
</details>

</Checkpoint>

## Recap

<RecapCard>
- Read a class in order: fields, constructor, public methods, callers.
- `OrbitCamera` wraps one camera: results, pose estimator, transform, and trust settings.
- The constructor takes a robot-to-camera transform and a camera name.
- The drivetrain loops over its cameras every cycle and feeds estimates to its pose.
</RecapCard>
