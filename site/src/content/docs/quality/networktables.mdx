## A shared table of named values

**NetworkTables** (NT) is a shared, typed key-value store: a list of named values that the robot and the tools on your laptop can both read and write.
On a real robot the values travel over the robot network. In simulation the connection stays on your own computer.

The current version, NT4, arrived with WPILib 2023. Its values are **typed**, so a number is a `double` and a flag is a `boolean`, and it reconnects on its own after a dropped connection.

## Tables and topics

Each value is a **topic**, named by a path. Take one from the flywheel:

```text
/Subsystems/FlywheelSubsystem/Tuning/kP
```

- `Subsystems/FlywheelSubsystem` is the **table**, the folder this subsystem owns.
- `Tuning/kP` is the topic name inside that table.
- The value is a `double`.

## Publishers and subscribers

- A **publisher** writes a value to a topic. The robot publishes velocity, target, and error.
- A **subscriber** reads the latest value from a topic, or a default you supply if none exists yet. AdvantageScope subscribes to what the robot publishes.

Both sides name the topic by its exact text. One changed character makes a different topic, and Java does not report an error.

## The flywheel's topic tree

This is every topic the Lab 5 flywheel publishes. The last five are used for tuning in lesson 4.3.

```text
/Subsystems
  /FlywheelSubsystem
    Velocity RPS        double
    Target RPS          double
    Error RPS           double
    Output Voltage      double
    At Target           boolean
    /Tuning
      kP                double
      kI                double
      kD                double
      kS Volts          double
      kV Volts per RPS  double
```

Notice the names. `Velocity RPS` tells a debugger six months from now what was measured and in which unit. A topic called `Speed` would not.

Why are these **fields** rather than local variables in `periodic()`? The robot calls `periodic()` about every 20 milliseconds, so a publisher created there would be built roughly 50 times a second.
Create each publisher once as a field and reuse it. The same rule applies to motors and controllers.

<GoDeeper title="why not SmartDashboard.putNumber()">
`SmartDashboard.putNumber()` also goes through NetworkTables, so older code still works. Publishers make the table, the topic, and the type explicit, and they keep the topic organized in a named tree in AdvantageScope's source list.
</GoDeeper>

## Checkpoint

<Checkpoint lesson="4.2">

<details>
<summary>What is the difference between a NetworkTable and a topic?</summary>
The table is the path that groups values, such as `Subsystems/FlywheelSubsystem`. A topic is one named, typed value inside it, such as `Velocity RPS`.
</details>

<details>
<summary>Why are publishers fields rather than variables in `periodic()`?</summary>
`periodic()` runs about 50 times a second. A publisher built there would be allocated again every loop. Building it once as a field and reusing it avoids that.
</details>

</Checkpoint>

## Recap

<RecapCard>
- NetworkTables is a shared, typed list of named values between the robot and your tools. NT4 arrived with WPILib 2023.
- A topic path is a table plus a topic name: `/Subsystems/FlywheelSubsystem/` plus `Velocity RPS`.
- Publishers write, subscribers read the latest value or a default.
- Always use `NetworkTableInstance.getDefault()`, and build publishers once as fields.
</RecapCard>
