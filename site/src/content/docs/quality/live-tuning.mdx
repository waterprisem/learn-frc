<WhyItMatters>
In lesson 3.5 every gain change meant editing Java, building, and redeploying, which takes a minute or more while the practice field clock runs.
With live tuning you change `kP` while the wheel is spinning and watch the graph react within a loop or two.
</WhyItMatters>

## The idea

The robot publishes its five gains as NetworkTables topics. A tool on your laptop edits a topic. The robot code reads the topic again every loop and gives the new number to the controller.

1. The robot publishes the starting gains from `Constants.java`, once.
2. You change a value in the tool.
3. A subscriber in `periodic()` reads it and updates the PID and feedforward.
4. You watch the graph, then repeat.

## The workflow

Live tuning is a loop with one final step you must not skip.

1. Hold a target and open the graph from lesson 3.5.
2. Change one gain in AdvantageScope or your dashboard.
3. Watch the graph and decide whether it improved.
4. Repeat until the response is good.
5. **Copy the final values into `Constants.java`** and redeploy.

Step 5 matters because live values exist only in the running program. When the robot restarts, the code publishes the old constants again and your tuning is gone.

## Before competition

Anything on the robot network can write these topics. A stray edit during a match, or a gain left at an experimental value, would change how the shooter behaves with no code change.

- Remove the tuning topics, or guard them so they only run in a test mode you enable on purpose.
- Make sure the values in `Constants.java` are the final tuned ones.

The lab does not set a guard. Where your team draws the line is a decision for you and your mentor.

<GoDeeper title="why the subscriber default matters">
Until a topic has a value, `get()` returns the default you gave `subscribe(...)`. Using the matching constant means a missing or unpublished topic leaves the robot on its known-good gains instead of zero.
</GoDeeper>

## Checkpoint

<Checkpoint lesson="4.3">

<details>
<summary>Why is changing a live gain faster than redeploying?</summary>
A redeploy means editing Java, building, and copying the program to the robot. A live edit only writes a number to NetworkTables, and the subscriber applies it on the next loop.
</details>

<details>
<summary>What could go wrong if a live tuning value is never copied back into `Constants.java`?</summary>
The next restart publishes the old constants and the tuning is lost. The robot performs worse than it did during practice and no one knows why.
</details>

</Checkpoint>

## Recap

<RecapCard>
- A subscriber reads a NetworkTables value every loop, so a gain can change while the robot runs.
- Publish the starting values once. Read and apply them at the start of `periodic()`.
- Workflow: edit live, watch the graph, repeat, then copy the final values into `Constants.java`.
- Live values vanish on restart. Remove or guard tuning code before competition.
</RecapCard>
