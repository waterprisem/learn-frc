## The checklist

In Lab 5 you swap `FlywheelSubsystem.java` and `Constants.java` with another pair and answer three questions. The aim is correctness and clarity, not rewriting clear code to match your taste.

| Question | What to look for |
|---|---|
| Is every tunable value in `Constants.java`, with a name that includes its unit? | Bare numbers in methods; names like `speed` or `limit` with no unit |
| Are sensor units clear from names, variables, or JavaDoc? | A parameter named `target`; a method that does not say if it returns RPS, RPM, or degrees |
| Is there behavior in `periodic()` that belongs in a command? | `periodic()` should log and poll. Deciding what the motor does is a command's job |

The lecture slides add two more things to watch for: constants that control motors (they should only store configuration), and unclear boundaries or silent failures.

## Giving a useful comment

A good comment has three parts.

1. **Where:** the file and the name, so the author can find it.
2. **What:** the specific problem, about the code and not the person.
3. **Why:** the impact, ideally with a suggested fix.

> `closedLoopCalculate` accepts `target` without a unit. Rename it to `targetRPS` so a future caller does not accidentally pass RPM.

"Looks good" gives the author nothing to act on. "I'd do it differently" is preference, not a finding. The lab asks for one recommended change per review. The authors then either make one review change or write down why they kept the design.

<Checkpoint lesson="4.5">

<details>
<summary>Why is "Looks good" not actionable?</summary>
It names no concrete issue and no next step. A useful comment is specific and explains the impact, like renaming `target` to `targetRPS` to prevent unit confusion.
</details>

<details>
<summary>You are the author and disagree with a finding. What do you do?</summary>
Discuss it with the reviewer, then either make a change or record the technical reason you intentionally kept the current design.
</details>
