<WhyItMatters>
A shooter wheel that spins at 38 rotations per second on a fresh battery might spin at 33 on a tired one, and the shot lands short.
Sending a fixed voltage (**open loop**) can't notice that. **Closed-loop** control measures the speed 50 times a second and adjusts the voltage to hold it.
</WhyItMatters>

## The idea

The code works out a motor voltage from two parts and adds them.

- **Feedforward predicts.** From the target speed alone, it estimates the voltage the wheel should need: `kS + kV × target`.
  `kS` is the small voltage that overcomes friction. `kV` is the volts needed per rotation per second (RPS).
- **PID corrects.** It compares the target with what the encoder measured and adds `kP × error`, where error = target − measured.
  This lab leaves `kI` and `kD` at 0.

<VelocityLoop />

Feedforward does most of the work, because it acts before any error appears. PID handles what the prediction missed, such as a sagging battery or a load.

The code also needs to say when the wheel is ready. The answer is a **tolerance**: the wheel counts as "at target" while the error is within 2 RPS.
A real wheel never sits at exactly 40.000, so the code never checks for an exact match.

<GoDeeper title="why At Target can stay true after you release the button">
`flywheelAtTarget` reads `flywheelPID.atSetpoint()`, which remembers the error from the last time the controller ran.
When you release the button the command ends and the controller stops running, so the last answer sticks until the next command starts and resets it.
You can see this in the playground: release from a settled speed and the At Target band continues while the wheel coasts down.
Later lessons add a check so that actions only trust readiness while the command is running.
</GoDeeper>

**On a real robot, also check**

- A small positive voltage spins the wheel in the direction the encoder counts as positive. If not, fix `FLYWHEEL_MOTOR_INVERTED` before closing the loop.
- Current limits are set, and nobody is near the wheel when you enable.
- Start with the lowest target. A real wheel has more friction than the simulation, so expect different `kS` and `kV` values.

## Checkpoint

<Checkpoint lesson="3.5">

<details>
<summary>What is the difference between feedforward and feedback?</summary>
Feedforward predicts the voltage from the target alone and never looks at the encoder. Feedback (PID) reads the encoder and corrects the error that remains.
</details>

<details>
<summary>What happens if `kP` is much too large? What about `kV` too small?</summary>
Too much `kP` over-corrects, so the speed swings above and below the target. Too little `kV` leaves the wheel steadily below the target.
</details>

<details>
<summary>Which four logged numbers would you look at if the flywheel never reached its target?</summary>
Target, measured velocity, error, and output voltage. Together they show whether the code asked for the right speed, how far off it is, and whether the controller is pushing at all.
</details>

<details>
<summary>Why does reaching the target not end the command?</summary>
The wheel has to keep holding the speed while the driver is ready to shoot. Readiness is a separate signal (`flywheelAtTarget`) that other commands can wait on.
</details>

</Checkpoint>

## Recap

<RecapCard>
- Output voltage = feedforward (`kS + kV × target`) + PID (`kP × error`).
- Feedforward predicts and does most of the work. PID corrects what is left.
- Tune one gain at a time: `kS`, then `kV`, then `kP`, checking all three targets.
- Steady error below the target means `kV` is too small. Swinging around the target means `kP` is too large.
- "At target" means the error is inside a tolerance, never an exact match.
</RecapCard>
