<WhyItMatters>
An arm that holds perfectly at its home position can sag or jump the moment it lifts, with no error message anywhere.
The usual cause is one wrong unit: angles in degrees going into code that expects radians. The code compiles, runs, and gives wrong voltages.
</WhyItMatters>

## Gravity changes with angle

An elevator fights the same weight at every height, so its `kG` is one steady voltage (lesson 3.7).
An arm does not. Gravity pulls straight down, but only the part of that pull that is **perpendicular to the arm** tries to rotate it.
That part is largest when the arm is horizontal and zero when it points straight up.

`ArmFeedforward` handles this by multiplying `kG` by the cosine of the angle. It predicts
`kS` (friction) + `kG × cos(angle)` + `kV × velocity` + `kA × acceleration`, using the profiled setpoint like the elevator did.
Angle 0 means horizontal. The Lab 7 value is `kG` = 0.16 V.

| Arm angle | cos(angle) | Holding voltage from kG |
| --- | ---: | ---: |
| 0° (horizontal) | 1.00 | 0.16 V |
| 30° | 0.87 | 0.14 V |
| 60° | 0.50 | 0.08 V |
| 90° (straight up) | 0.00 | 0.00 V |

## The radians trap

`ArmFeedforward` expects the angle in **radians** and the velocity in radians per second. The rest of the arm code uses degrees, because degrees are easy to read in logs and goals.
Java will not stop you from passing degrees: both are just a `double`.

The cosine of a degree value, read as radians, is nonsense. At 30° you would get cos(30) = 0.15 instead of 0.87. At 60° it is -0.95, so gravity help points the wrong way.
At 0° the answer happens to be right, which is why this bug hides at the home position.

| Arm angle | Correct: cos(angle in radians) | Bug: cos(angle in degrees) |
| --- | ---: | ---: |
| 0° | 1.00 | 1.00 |
| 30° | 0.87 | 0.15 |
| 60° | 0.50 | -0.95 |
| 90° | 0.00 | -0.45 |

## Where Lab 7 converts

The rule is to convert at the edge. Everything inside the subsystem is in degrees, and the one place that needs radians converts right there.

**1. The sensor edge.** The motor reports mechanism rotations. Helpers turn them into degrees before anything else sees them.

<GoDeeper title="the other direction">
Some code stores angles in radians and converts to degrees for display. The rule is the same: pick one unit for inside the subsystem, put the unit in every name (`targetAngleDegrees`), and convert once at each edge.
Never convert the same value twice.
</GoDeeper>

3. Run each experiment on its own, restart the simulation, then restore the value.

| What you do | What you see | What it tells you |
| --- | --- | --- |
| Remove `Math.toRadians(...)` in the feedforward | Compiles, but the arm holds and moves worse, and the output voltage is wrong at angles away from 0° | The cosine received degrees |

**On a real robot, also check**

- Zero position: the code assumes 0° is horizontal. If your arm's zero is somewhere else, the cosine is applied to the wrong angle.
- The mechanism's min and max angle are set so the arm cannot drive into a hard stop.

## Checkpoint

<Checkpoint lesson="3.8">

<details>
<summary>Why does an arm need different gravity compensation at 0 degrees and 90 degrees?</summary>
At 0° the arm is horizontal and gravity pulls straight across its lever, so it needs the most holding voltage. At 90° the arm points straight up, gravity pulls along it, and no voltage is needed. `ArmFeedforward` models this with `kG × cos(angle)`.
</details>

<details>
<summary>Why is there no button binding for HOME?</summary>
`HOME` is the default command: what the arm does whenever no level button is held. Releasing a `whileTrue` button ends that command and the default takes over.
</details>

</Checkpoint>

## Recap

<RecapCard>
- Arm gravity voltage is `kG × cos(angle)`: largest horizontal, zero vertical.
- `ArmFeedforward` takes radians and radians per second. Degrees compile but give wrong voltages.
- Keep degrees inside the subsystem and convert once, at the feedforward call, with units in every name.
- The radians bug looks fine at 0° and wrong elsewhere.
</RecapCard>
