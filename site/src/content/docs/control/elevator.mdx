<WhyItMatters>
A flywheel only has to hold a speed. An elevator has to travel to a height, stop there, and then keep holding the carriage up against gravity, with the motor doing real work even when nothing moves.
Lesson 3.6 planned the trip; this lesson adds the two WPILib objects that follow the plan and carry the weight.
</WhyItMatters>

## Two objects, two jobs

- **`ProfiledPIDController`** is a PID controller with a trapezoid profile built in. You give it a goal; each loop it moves its profiled setpoint along the plan and returns a correction for the measured height. Its constructor takes `kP`, `kI`, `kD`, and the `TrapezoidProfile.Constraints` from lesson 3.6.
- **`ElevatorFeedforward`** predicts voltage from a model. It never reads the encoder.

The calls you use:

| Call | What it does |
|---|---|
| `setGoal(...)` or the second argument of `calculate` | The final height |
| `calculate(measurement, goal)` | Advances the profile one loop and returns the PID volts. Measurement first. |
| `getSetpoint()` | The profiled setpoint, with `.position` and `.velocity` |
| `getGoal().position` | The goal you gave it |
| `reset(position, velocity)` | Restarts the profile from where the mechanism really is |
| `atGoal()` | True when the height is within tolerance of the goal |

## Feedforward with gravity

`ElevatorFeedforward` has three main gains, plus a fourth the lab also sets.

| Gain | Meaning |
|---|---|
| `kS` | Volts to overcome friction and start moving |
| `kG` | **Constant volts that hold the carriage against gravity** |
| `kV` | Volts per meter per second of velocity |
| `kA` | Volts per meter per second squared of acceleration (the lab sets it, 0.05) |

`kG` is one number at every height, because gravity pulls the same everywhere on a vertical lift. The flywheel needed voltage only to spin. The elevator needs `kG` even at zero speed, so the PID does not have to build up error just to hold still.

## How Lab 6 combines them

```text
output = PID(measured height, goal)  +  feedforward(setpoint velocity)
```

Feedforward gets the **setpoint** velocity, not the goal, because it needs to know how fast the plan is moving now. The goal is a position, not a speed.

## What you see, what you change

Tune in the order the lab sets things up: PID starting gains, then the constraints, then the feedforward gains. Change one thing at a time, then restore it.

| What you see on the graph | What to change |
|---|---|
| With `FEEDFORWARD_KG_VOLTS` at 0.0, error grows and output works harder near each goal | `kG` is too small: restore it so feedforward carries the weight |
| Profiled setpoint takes longer to reach the goal (lab: `MAX_VELOCITY_METERS_PER_SECOND` at 0.4) | The max velocity is low: raise it for a snappier move |
| Height overshoots or oscillates | `PID_KP` too large (or `PID_KD`): reduce it |
| Elevator jumps or overshoots at the start of a move | Reduce `PID_KP`, `PID_KD`, or max acceleration; check the reset is in `initialize()` only |
| Output stays at 0 and nothing moves | A constant, such as the PID or constraints, is still zero |
| `At Target` never turns true | `setTolerance()` is missing, or `periodic()` does not assign `atGoal()` |

<GoDeeper title="why the height trails the setpoint with the lab gains">
The simulated elevator needs about 8.6 V for every meter per second, and about 0.18 V to hold still.
The lab's `kV` of 1.10 predicts far less than that, so during a move the PID has to supply the rest, and it can only do that once the error has grown.
Raise `kV` toward 8.6 and feedforward does the work instead, so the height stays on the profiled setpoint.
</GoDeeper>

## Checkpoint

<Checkpoint lesson="3.7">

<details>
<summary>Why does an elevator need <code>kG</code>?</summary>
Gravity pulls on the carriage all the time, so holding a height takes a constant voltage. `kG` supplies it, so the PID only corrects small errors instead of fighting gravity alone.
</details>

<details>
<summary>Why reset with both position and velocity, and why in <code>initialize()</code>?</summary>
The profile must start from where the mechanism really is, including how fast it is moving. Resetting in `initialize()` does that once; resetting in `execute()` would restart the profile every 20 ms.
</details>

<details>
<summary>How could a later scoring command use <code>elevatorAtTarget</code>?</summary>
It can wait for the trigger to be true, so the mechanism only scores once the elevator is within tolerance of its goal.
</details>

</Checkpoint>
