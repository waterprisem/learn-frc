<WhyItMatters>
A shooter should not feed a game piece until the wheel is up to speed, and the arm should be in place before the wheel starts.
If "ready" is true too early, the robot fires at the wrong moment, and it only happens sometimes.
</WhyItMatters>

## The subsystem says when it is ready

Other parts of the robot should not read encoders and compare numbers themselves. The subsystem owns that knowledge and shares one yes-or-no answer.
In WPILib that answer is a **Trigger**: an object that is true or false and that commands can react to.

The flywheel from Lab 4 shows the pattern.

The yes-or-no comes from the controller's **tolerance** (lesson 3.5): the error must be inside 2 RPS, never exactly zero.
The arm in Lab 7 does the same with `armAtTarget`, with a 2 degree tolerance.

## At setpoint is not at goal

A profiled controller (lessons 3.6 and 3.7) has two targets. The **goal** is where you want to end up. The **setpoint** is where the profile says the mechanism should be right now.

`atSetpoint()` asks whether the mechanism is near the setpoint. The profile starts at the mechanism's position and moves smoothly, so the answer is nearly always yes.
Your arm would be "ready" the instant you pressed the button, while still far from where you asked it to go.

`atGoal()` asks whether the mechanism is near the **goal** and the profile has finished. That is the question readiness needs. The Lab 7 arm uses it:

```java
armAtAngle = armPID.atGoal();
```

| Controller | Ready check |
| --- | --- |
| Flywheel (plain PID) | `atSetpoint()` |
| Arm, elevator (profiled) | `atGoal()` |

## The race condition

"The arm is at its goal" is not enough. The controller already has a goal before your new command runs.
Say the arm is settled at the Intake angle, so `armAtTarget` is true. The driver switches to Score Amp.
For a moment `armAtTarget` is still true, for the **old** goal. A wait on it ends at once, and the flywheel starts before the arm has moved.

Lab 9 calls this a race condition. The fix is to make each trigger prove two things: the goal is the one you are waiting for, and the mechanism is there.

<GoDeeper title="comparing doubles with ==">
Comparing doubles with `==` is usually risky, because calculated values can differ in the last digits. Here the goal is set straight from a named constant and never calculated, so the values match exactly.
</GoDeeper>

## Checkpoint

<Checkpoint lesson="3.9">

<details>
<summary>Why does a flywheel check use a tolerance instead of an exact match?</summary>
A real wheel never sits at exactly the target. The check is true while the error is inside the tolerance (2 RPS in Lab 4), so the code compares against a range.
</details>

<details>
<summary>Why can a goal-specific trigger be safer than `armAtTarget`?</summary>
`armAtTarget` can be true for the previous goal. A goal-specific trigger also checks that the goal is the one the sequence needs, so it cannot fire early on a stale goal.
</details>

</Checkpoint>

## Recap

<RecapCard>
- A subsystem shares readiness as a public `Trigger`, refreshed in `periodic()` from the controller's tolerance.
- Plain PID uses `atSetpoint()`. Profiled controllers use `atGoal()`, because the setpoint is reached almost at once.
- A generic "at target" can be true for the old goal. That is the race condition.
- Make the trigger say what you need: goal equals the wanted constant, and the mechanism is there.
</RecapCard>
