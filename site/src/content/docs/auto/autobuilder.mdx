<WhyItMatters>
PathPlannerLib knows how to follow a curve, but it has never seen your robot. It does not know how you read the pose or which method makes the wheels move.
**`AutoBuilder.configure`** is where you hand it those pieces, once, so that any auto file can run on your drivetrain.
</WhyItMatters>

## What AutoBuilder needs

Think of it as a short list of questions about your robot, answered with code.

1. Where am I? A pose supplier.
2. Start from here. A way to reset the pose.
3. How fast am I moving? A supplier of robot-relative speeds.
4. Move like this. A way to drive with speeds (and feedforwards).
5. How hard should I correct? A path-following controller with PID constants for translation and rotation.
6. What can this robot do? The robot config (mass, wheels, limits).
7. Am I red? A "should flip" supplier.
8. Who drives? The drive subsystem, so the scheduler knows the path owns it (lesson 2.4).

## Alliance flipping

You draw every path on the blue side of the field. When the flip supplier returns true, PathPlannerLib mirrors the whole path and its poses to the red side (lesson 6.1 explains the field coordinates).
You maintain one set of paths instead of two. The supplier is checked when the auto starts, so the alliance must be known by then.

## Loading and choosing an auto

`new PathPlannerAuto("L1")` loads the file `autos/L1.auto` by name. The team builds one of each in `RobotContainer`, adds them to a `SendableChooser`, and publishes it to the dashboard.

At the start of autonomous, `Robot` calls `getAutonomousCommand()`, which returns `autoChooser.getSelected()`, and schedules it.

The auto file also has `resetOdom: true`, which makes the pose start at the path's first point. That is how the robot knows where it started. If the robot is placed somewhere else, the auto still believes it is at the start point.

<GoDeeper title="the warmup command">
The first time PathPlannerLib runs it can stall the robot for a moment while Java loads classes. The team schedules `FollowPathCommand.warmupCommand()` at the end of the `RobotContainer` constructor so that happens before the match, not during it.
</GoDeeper>

## Checkpoint

<Checkpoint lesson="8.2">

<details>
<summary>Why does AutoBuilder need both a pose supplier and a reset-pose method?</summary>
The supplier lets the follower see where the robot is every loop. The reset lets an auto set the starting pose to its first path point.
</details>

<details>
<summary>An auto starts in the wrong place on the field. Name two things to check.</summary>
Whether the robot was placed at the path's start pose, and whether `resetOdom` is on. After that, check whether the alliance was known at start so the flip was correct.
</details>

</Checkpoint>

## Recap

<RecapCard>
- `AutoBuilder.configure` answers PathPlannerLib's questions about your drivetrain, once, at startup.
- It needs pose, reset, speeds, a drive method, follower PID, robot config, a flip rule, and the drive subsystem.
- Paths are drawn on the blue side; the flip supplier mirrors them for red.
- `new PathPlannerAuto("name")` loads an auto; a chooser selects it; `getAutonomousCommand()` returns it.
</RecapCard>
